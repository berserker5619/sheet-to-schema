# sheet-to-schema 1.1 Spec — Browser File Reader (CSV and xlsx) & Streaming Grouping

Oct 18, 2026 · @Nizamudeen S

## Purpose and scope

sheet-to-schema 1.1 adds two things, both additive: an official browser file reader for CSV and `.xlsx` that matches the server's `readSheet` by construction, and grouping in the streaming `runImport` for both formats. No 1.0 API changes shape; semver applies.

**Baseline:** sheet-to-schema 1.0.0 (`2c4e9ec`, repo `berserker5619/sheet-to-schema`); Dynamic Entity 3.0.0 depends on `^1.0.0` and runs a daily drift check against `latest` and `next`. Rules this spec relies on are in this repo's `docs/import-phase1-spec.md` (grouping §5, results §9) and in Dynamic Entity's [`docs/rc-feedback.md`](https://github.com/berserker5619/Dynamic-Entity/blob/main/docs/rc-feedback.md) (R3-1, deferred items). Where this spec and phase1 disagree, this spec wins; each such point is named where it is made.

**In scope**

- A: `sheet-to-schema/browser`, a browser-safe reader that takes a CSV, TSV or `.xlsx` file and returns the same grid the server's `readSheet` produces.
- B: `runImport` executes grouped plans (contiguous only), for CSV and `.xlsx` alike, with bounded memory.
- A capability field on preview responses so clients know a server can group.

**Non-goals for 1.1**

- Non-contiguous grouping in the streaming runner (still refused; the browser path keeps supporting it).
- Nested grouping (a collected list inside a collected list).
- Choosing a sheet other than the first, or a header row other than row 1.
- Legacy `.xls`, and a zero-dependency in-house xlsx parser (see Open questions).
- The Angular mapping screen (Phase 4).

**Using this with Claude Code:** every MUST is a test. Implement in the order given in the last section; anything listed as an open question is decided by the owner, not in code.

## Feature A: the browser file reader (CSV and xlsx)

`sheet-to-schema/browser` reads a CSV, TSV or `.xlsx` file in the browser and returns the same grid the server's `readSheet` produces, so browser and server import any supported file identically by code, not by documentation.

**Problem.** Today the browser path depends on a parser each app supplies. Round 3 showed the cost: the SheetJS example truncated characters above U+FFFF (R3-1), and earlier rounds needed a written contract for merged cells and typed values. DE 3.0 now documents an ExcelJS parser, but every app still copies it.

**Decision: one entry for both formats, sharing the server's rules.** The format is decided by the file's first bytes, exactly as `readSheet` does. CSV goes through the main entry's existing parser and delimiter detection, and never loads `exceljs`. `.xlsx` goes through ExcelJS, loaded on first use, with the server's cell rules; ExcelJS stays an optional peer. A zero-dependency xlsx reader is deferred (Open questions).

**API**

```typescript
// sheet-to-schema/browser — browser-safe; also runs in Node 20+
export interface ReadSheetFileOptions {
  filename?: string;   // a delimiter hint only: ".tsv" means tab, as on the server
  limits?: Partial<Pick<ImportLimits,
    'maxBytes' | 'maxRows' | 'maxColumns' | 'maxCellLength' | 'maxZipEntries'>>;
}
export interface SheetFile extends SheetGrid {   // { headers: string[]; rows: unknown[][] }
  format: 'csv' | 'xlsx';
  delimiter?: CsvDelimiter;                      // CSV only
}
export function readSheetFile(
  input: Blob | ArrayBuffer | Uint8Array,
  options?: ReadSheetFileOptions,
): Promise<SheetFile>;

// Lower-level, same rules, for callers that already know the format:
export function readXlsx(input: Blob | ArrayBuffer | Uint8Array,
  options?: Omit<ReadSheetFileOptions, 'filename'>): Promise<SheetGrid>;
```

`SheetGrid` is exported from the main entry if it is not already (additive). An app plugs `readSheetFile` into its own file-parsing hook (DE's `SheetParser`) in one line. The returned `delimiter` lets the caller pass the same decimal mark the server derives (`decimalMarkFor(delimiter)`), so a semicolon file reads `1,5` as 1.5 on both sides.

**Cell rules — one function, used by both readers.** Extract the server's per-cell logic (`cellValue` in `xlsx-source`) into a shared module both readers call. The rules, unchanged from the server today:

| Cell | Value in the grid |
| --- | --- |
| Date (incl. 1904 workbooks) | `Date` at UTC midnight for a date-only value |
| Number, boolean | as typed |
| Formula | its cached result, never the formula text |
| Rich text, hyperlink | the joined text |
| Error | the error text, e.g. `#N/A` |
| Covered cell of a merged range | `''`; the master cell keeps the value |
| Text with characters above U+FFFF | intact (the R3-1 fixture) |

Rows and sheets follow the server exactly: the lowest-numbered `sheetN.xml` is read; blank rows are kept as `[]` so row numbers match the spreadsheet; headers are row 1 rendered through `cellText`.

**CSV rules — the server's, unchanged.**

| Input | Result |
| --- | --- |
| UTF-8, with or without a byte-order mark | read; the mark is stripped from the first header |
| Delimiter | `.tsv` filename means tab; otherwise `,`, `;` or tab detected from the header line outside quotes; a tie or a single column means `,` |
| Quoted fields with delimiters, quotes or line breaks | one cell each (RFC 4180) |
| UTF-16, legacy `.xls`, a zip that isn't a workbook | refused with `UNSUPPORTED_FORMAT`, naming what it is |
| Any other bytes, including a binary that isn't a zip | read as CSV, exactly as the server reads them: the same grid, and the same per-row problems from the mapping. Not refused (refusing non-text bytes is an open question for 2.0) |
| Short and long rows | short rows padded to the header width; blank lines kept so row numbers match |

The browser holds the whole file, so CSV is parsed in one pass rather than streamed; the parser is the same state machine the server streams through.

**Limits and errors.** Both formats enforce `maxBytes`, `maxRows`, `maxColumns` and `maxCellLength` with the server's defaults; `.xlsx` also enforces `maxZipEntries` and checks the zip's central directory (entry count, declared sizes, compression ratio) before ExcelJS sees the bytes. Inflate-time checks stay server-only: in a browser the file is the user's own and only their tab is at risk, which the README states. Errors reuse the server's codes (`UNSUPPORTED_FORMAT`, `MALFORMED_FILE`, `SHEET_TOO_LARGE`), and a missing `exceljs` throws the same install message as `/node`, only when an `.xlsx` is read.

**Bundle rules.** The main entry is unchanged and dependency-free. The `/browser` entry has no static import of `exceljs` and no Node built-ins, and a CSV-only app that imports it never downloads ExcelJS. The bundle check enforces all three, as it does for `/node`.

## Feature B: grouping in the streaming runImport

`runImport` executes grouped plans with contiguous groups, for CSV and `.xlsx` alike, producing exactly what `applyMapping` produces for the same rows, with memory bounded by the batch plus the largest group. Grouping works on rows after reading, so it is format-agnostic by design; the tests prove it for both.

**Today.** `applyMapping` groups in memory. `runImport` refuses any plan with `group` before reading a row (`INVALID_PLAN` carrying `PLAN_GROUP`). The grouping rules (tuple keys, first row wins with a `RECORD_GROUP_CONFLICT` warning, collected arrays, `rows` on problems, the closed-key set) are already specified in phase1 §5 and implemented for `applyMapping`. The three memory limits are specified there but enforced nowhere yet.

**Decision: one group accumulator, used by both.** Extract the grouping into an internal `GroupAccumulator` that takes rows one at a time and emits finished records. `applyMapping` feeds it every row; `runImport` feeds it batch by batch. One implementation means parity by construction, and today's `applyMapping` tests become its first gate.

- **Contiguous mode** (default): a key change closes the open group and emits its record. A closed key seen again fails with `GROUP_NOT_CONTIGUOUS`, naming the key and both row numbers.
- **Non-contiguous mode** buffers every group until the end. Only `applyMapping` may use it; `runImport` still refuses `contiguous: false` with `PLAN_GROUP`.

**Batching.** `batchSize` counts rows read, as today. The runner reads a batch, feeds the accumulator, and calls `onBatch` with the records it has finished; an open group is carried into the next batch, never split. `onBatch` is still awaited, so backpressure holds. At end of file the open group is flushed.

**Memory and limits.** Peak memory is the current batch, the open group, and the closed-key set. All three are bounded by limits that already exist in the spec, enforced while streaming:

| Limit | Default | Error when exceeded | HTTP (server only) |
| --- | --- | --- | --- |
| `maxGroupRows` | 10,000 rows in one group | `GROUP_TOO_LARGE` | 413 |
| `maxGroups` | 200,000 closed keys | `TOO_MANY_GROUPS` | 413 |
| `maxGroupKeyBytes` | 8 MiB of closed keys | `TOO_MANY_GROUPS` | 413 |
| (contiguity) | — | `GROUP_NOT_CONTIGUOUS` | 422 |

The limits live in the main entry, so the dependency-free engine and the server share one definition:

```typescript
// sheet-to-schema (main entry)
export interface GroupLimits {
  maxGroupRows: number;
  maxGroups: number;
  maxGroupKeyBytes: number;
}
export const DEFAULT_GROUP_LIMITS: GroupLimits;   // the defaults above

export interface ApplyMappingOptions {
  // ...the 1.0 options, unchanged
  groupLimits?: Partial<GroupLimits>;             // overrides; each falls back to its default
}

// sheet-to-schema/node
export interface ImportLimits extends GroupLimits { /* ...the 1.0 limits, unchanged */ }
```

`applyMapping` enforces them by default, through the same `GroupAccumulator` the runner uses. This supersedes phase1 §5, which said `applyMapping` does not apply the memory limits.

| Limit | Contiguous mode | Non-contiguous mode (`applyMapping` only) |
| --- | --- | --- |
| `maxGroupRows` | enforced | enforced |
| `maxGroups` | enforced: closed keys | enforced: distinct keys |
| `maxGroupKeyBytes` | enforced: closed keys | not enforced (the whole sheet is held anyway) |

A limit or contiguity failure is the same failure object in both: an `ImportFailure` with the code above and `details` (`key`, `rows`). `applyMapping` throws it; `runImport` throws it and the router maps its code onto the HTTP status, which exists only on the server.

These stop the whole import. Because imports are not transactional, earlier batches may already be written; `/validate` runs the same pipeline without writing, so it catches every one of these before anything is stored. The README says to validate grouped imports first.

**Results.** Counts follow phase1 §9: `rowsRead`, `imported` (records), `rowsInImported`, `skipped`, `failed` (rows), `errorCount`, `warningCount`, with `rowsInImported + skipped + failed === rowsRead` always. A record-level problem carries `rows` (every row of its group); a cell problem carries its own row; identical problems in one record merge. A row error anywhere in a group fails the whole record.

**Telling clients the server can group.** A 1.0 server accepts `planVersion: 2` but refuses `group`, so `planVersions` alone can't tell a client whether grouping works. Preview responses gain `features: string[]` (additive), listing `"group"` from 1.1. The router's `/validate` and `/import` accept grouped plans.

`planForServer` gains a second form; the first is unchanged:

```typescript
// 1.0 form, unchanged: checks plan versions only, never refuses for `group`.
export function planForServer(plan: unknown, planVersions: readonly number[] | undefined): PlanForServer;
// 1.1 form: the preview, or the part of it this needs.
export function planForServer(plan: unknown, preview: { planVersions?: number[]; features?: string[] }): PlanForServer;
```

The two are told apart by the second argument: an array or `undefined` is the 1.0 form, an object is the 1.1 form. The 1.1 form does everything the 1.0 form does, and also refuses a plan with `group` unless `features` includes `"group"`. A missing `features` (a 1.0 server) means no grouping. A refusal names `group` in `refused`, as other refusals name their paths.

## Compatibility and the Dynamic Entity follow-up

1.1.0 is a minor release: every change is an addition, and DE 3.0's `^1.0.0` range picks it up, so DE's drift check is the first consumer test.

**What changes for 1.0 users**

- New `sheet-to-schema/browser` entry with `readSheetFile` (CSV and `.xlsx`) and `readXlsx`; `SheetGrid` exported if not already.
- `runImport` and the router accept grouped plans they used to refuse. Nobody can depend on that refusal usefully, so this is treated as a feature, not a break; the CHANGELOG says so.
- Preview responses gain `features`. Older clients ignore it.
- New limits `maxGroupRows`, `maxGroups`, `maxGroupKeyBytes`: `GroupLimits` and `DEFAULT_GROUP_LIMITS` in the main entry, included in `ImportLimits`, with the defaults above. All optional, all with defaults. The three error codes already exist in 1.0's `IMPORT_FAILURE_CODES`.
- `applyMapping` now enforces the group limits. A grouped sheet past a default (a group of more than 10,000 rows, more than 200,000 keys) throws where 1.0 imported it; `groupLimits` raises the limit. The CHANGELOG says so.
- `planForServer(plan, preview)` is a new form; `planForServer(plan, planVersions)` behaves exactly as in 1.0.
- Peer dependencies unchanged: `exceljs`, `busboy` and `express` stay optional; a CSV-only browser app needs none of them.

**Mixed versions**

| Client | Server | Grouped plan |
| --- | --- | --- |
| 1.1 `planForServer(plan, preview)` | 1.1 | sent and imported |
| 1.1 `planForServer(plan, preview)` | 1.0 (no `features`) | refused before upload, with a message to upgrade the server |
| 1.0 `planForServer`, or 1.1 with `(plan, planVersions)` | 1.1 | sent and imported (the client doesn't check `group`; the server can group) |
| 1.0 `planForServer`, or 1.1 with `(plan, planVersions)` | 1.0 | sent, and refused by the server with `PLAN_GROUP`, as today |
| any | DE server before 3.0 | refused, as today (`planVersions` lacks 2) |

**Dynamic Entity 3.1 (separate work, after 1.1.0 ships)**

- DE's default browser parser (CSV only today) and the EXTENDING xlsx example both become one-line wrappers over `readSheetFile`, so DE reads CSV and `.xlsx` in the browser out of the box; the documented-parser test keeps running against it.
- DE's server wrapper passes `features` through, and `HttpImportTransport` calls the `planForServer(plan, preview)` form.
- The wizard still has no way to build a grouped plan; that is the Phase 4 mapper. Until then, grouping over HTTP is reachable from code.

## Acceptance criteria

1.1.0 is done when every box below is a passing test, and every 1.0 test still passes unchanged.

**A: browser reader**

- [ ] xlsx parity: for each fixture, `readSheetFile` (under jsdom and under Node) returns exactly the headers and rows the server's `readSheet` returns. Fixtures: 1904 dates, numeric IDs incl. an unsafe integer, the merged/complex sheet (hidden column, formula, two sheets, trailing blanks, duplicate headers), the openpyxl emoji file, Tamil text, typed cells, error cells, blank rows mid-sheet.
- [ ] CSV parity, same comparison: Excel "CSV UTF-8" with a byte-order mark, Excel semicolon CSV with decimal commas, a `.tsv` (by filename) whose header has more commas than tabs, Google Sheets export with multi-line quoted cells and escaped quotes, Tamil and emoji, ragged rows, blank lines. Each reports the same `delimiter` as the server.
- [ ] Records parity: all those fixtures through `readSheetFile` + `applyMapping` (decimal mark from the returned delimiter) and through the server router give identical records, errors and warnings.
- [ ] R3-1: "Rajesh Kumar 🎉" from the openpyxl fixture survives the browser path.
- [ ] Extracting the shared xlsx cell rules changes no server test result.
- [ ] Each limit is enforced with the server's error code; an over-limit zip (too many entries, declared ratio past the limit) is refused before ExcelJS loads.
- [ ] UTF-16 text, `.xls` and a `.docx` are refused with the server's codes and messages; a random binary that isn't a zip is read as CSV into exactly the grid the server reads.
- [ ] Without `exceljs` installed, reading a CSV works and reading an `.xlsx` throws the install message; importing `sheet-to-schema/browser` alone loads nothing.
- [ ] Bundle check: the `/browser` entry has no static `exceljs` import and no Node built-ins; a CSV-only test bundle contains no ExcelJS code; the main entry still has zero dependencies. Each rule proven by a planted violation.

**B: streaming grouping**

- [ ] Extracting `GroupAccumulator` changes no `applyMapping` test result.
- [ ] `applyMapping` enforces each group limit by default with its code, in the modes the table above gives (`maxGroupKeyBytes` not in non-contiguous mode), and `groupLimits` overrides each; the thrown `ImportFailure` is the one `runImport` throws for the same rows.
- [ ] Parity: for the order fixture and every grouping fixture, `runImport` at `batchSize` 1, 2, 3 and 500, fed one byte at a time, gives exactly `applyMapping`'s records, errors, warnings and counts.
- [ ] A group straddling a batch boundary is one record; `onBatch` never receives a partial group.
- [ ] A closed key reappearing gives `GROUP_NOT_CONTIGUOUS` naming the key and both rows; each limit gives its code; each is caught by `/validate` with nothing written.
- [ ] `contiguous: false` is still refused by `runImport` with `PLAN_GROUP`.
- [ ] 50,000 rows in groups of 5 stay under a heap bound set at about 1.5× the measured value, proven to fail under a planted leak.
- [ ] `rowsInImported + skipped + failed === rowsRead` on every grouping fixture.
- [ ] Previews list `features: ["group"]`; `planForServer(plan, preview)` refuses a grouped plan for a preview without it, and for one with no `features` field; `planForServer(plan, planVersions)` gives exactly its 1.0 results.

**Release**

- [ ] Streaming grouping proven on both formats: the order fixture as CSV and as `.xlsx` gives identical results through `runImport`.
- [ ] The consumer check installs the packed tarball and runs a grouped import over HTTP, plus a CSV and an `.xlsx` read through `readSheetFile` in a browser bundle.
- [ ] DE's drift workflow passes against 1.1.0 before DE 3.1 work starts.

## Order of work and open questions

Refactors land first with no behaviour change, so each new feature starts from a proven base. One commit per step, full gate green after each.

1. **A1** Extract the shared xlsx cell rules from `xlsx-source`, and the format sniffing from `readSheet`, into browser-safe modules; server results unchanged.
2. **B1** Extract `GroupAccumulator` from `applyMapping`; results unchanged. Then `GroupLimits` in the main entry, enforced by `applyMapping`.
3. **A2** `sheet-to-schema/browser`: `readSheetFile` for CSV and `.xlsx`, `readXlsx`, the zip pre-checks, and the CSV and xlsx parity fixtures.
4. **A3** Bundle and consumer checks for `/browser`, including the CSV-only bundle.
5. **B2** Grouping in `runImport`: batching, the three limits, `GROUP_NOT_CONTIGUOUS`, counts, on both formats.
6. **B3** `features` on previews and `planForServer`'s check; the router accepts grouped plans.
7. **Release** 1.1.0-rc.1 to `next`, a short test round (the Round 3 harness plus a grouped HTTP import of a CSV and an `.xlsx`), then 1.1.0. DE's drift job must pass on the rc.

**Open questions (owner decides)**

- [ ] Should 2.0 replace ExcelJS with a zero-dependency reader (zip via `DecompressionStream`, a small XML scanner) used by both sides? It would drop the heaviest peer and the uuid alert, at the cost of owning an xlsx parser.
- [ ] Is 10,000 rows the right default for `maxGroupRows`, or should it scale with `batchSize`?
- [ ] Should a sheet-selection option come in 1.2, added to both readers at once?
- [ ] Should the browser reader also run inflate-time zip checks, given it's protecting only the user's own tab?
- [ ] Should 2.0 refuse non-text bytes (a binary that isn't a zip) instead of reading them as CSV, on both readers at once? 1.x reads them as CSV, and the mapping reports the nonsense rows one by one.
