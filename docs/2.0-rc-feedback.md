# sheet-to-schema 2.0 release-candidate feedback

Findings from testing the published 2.0 release candidates in fresh projects outside the
repository, installed from npm, never from this repository's source. Nothing here is fixed in
the round that found it. The scripts are in [`test-harness/2.0-rc1/`](../test-harness/2.0-rc1/README.md).

Severity: **High** blocks the release; **Medium** is wrong behaviour a user can meet, to fix
before 2.0.0; **Low** is a rough edge or a documentation gap; **Info** is worth knowing and
needs no change.

### Findings

| ID | Severity | Finding | Case |
| --- | --- | --- | --- |
| R1-1 | Medium | **The polling recipe keeps a cancelled or failed import's file.** It deletes the upload only after an import that succeeds (`.then` of the import job). A cancelled import (`ABORTED`) or one that failed leaves the file on disk until the expiry sweep, up to 24 hours later. That is the user's data, kept for a day after they cancelled. The recipe's own text says "the file is deleted after the import". Whether to keep it for a retry or delete it, the recipe should do one on purpose and say which. | c |
| R1-2 | Low | **`readCsvFile` calls a zip that is not a workbook "an .xlsx workbook".** For a zip of a CSV, the other four entry points say `This is a zip archive that is not an Excel workbook. Upload an .xlsx or .csv file.`. `readCsvFile` says `This is an .xlsx workbook. Read it with readSheetFile from sheet-to-schema/browser, or save it as CSV.` Same code (`UNSUPPORTED_FORMAT`), but a different message, and a wrong one: it decides "workbook" from `PK` alone. | e |
| R1-3 | Low | **`grouping: false`'s refusal still speaks as 1.x.** `GROUPING_NOT_STREAMED` reads "This server version does not group rows into records yet. The browser import does…". In 2.0 the server groups by default, and `grouping: false` is the app's choice, so "this server version … yet" is untrue. | d |
| R1-4 | Low | **Progress leads the import, in coarse steps.** `bytesRead` counts bytes pulled from the input, which includes the reader's read-ahead: the 8 KB classification peek, and a file stream's 64 KB chunks. At the cancel in (c), progress was 6.9% while 2.5% of rows had been read (1,500 of 60,000). Across a 1.2 MB import, 120 batches gave 16 distinct progress values. This is as documented ("bytes consumed from the input"). The recipe calls it a progress bar without saying it moves in read-ahead steps. | c |
| R1-5 | Low | **The recipe's file modes do nothing on Windows.** It creates the directory `0o700` and files `0o600` and calls them "readable by this process only". On Windows Node ignores both, and the files are created `0o666`. | c |
| R1-6 | Info | `latest` is still 1.3.0 on the registry, read three times during the round (`--prefer-online`), not 1.3.1. | — |
| R1-7 | Info | `previewSheet`'s suggestion never proposes a group, because it is made from headers alone, as documented. An app that sends the preview's suggestion back as the plan therefore imports one record per row, until the person (or `suggestMapping(headers, adapter, { sample })`) adds the group. | d |

### a. MIGRATING-2.0's Express example

The block was extracted from `MIGRATING-2.0.md` at `v2.0.0-rc.1` (32 lines) and compiled
unchanged. It type-checks with `@types/express` 4.17.25 and 5.0.6, strict, with `skipLibCheck`
off and on. Built with esbuild and run, each server answered:

- CSV and `.xlsx` preview: `headers`, `rowCount` 3, `format`, a suggestion;
- validate: `written: false`, `imported` 2, `failed` 1, the error on row 4;
- import: `written: true`, `imported` 2;
- a plan that is not JSON: 400 `INVALID_PLAN`; no plan field: 400, naming "before the file";
- a PNG named `.csv`: 415 `UNSUPPORTED_FORMAT`; no file: 400 `NO_FILE`;
- and it was still answering afterwards. Nothing was logged.

### b. node:http

The same routes on `node:http` with `receiveUpload`, `readPlanField`, `previewSheet`, `runImport`
and `toErrorBody`: 11/11, the same answers.

### c. The polling recipe

The recipe was copied from the README at the tag. It type-checks unchanged (strict,
`skipLibCheck` off). The harness changed one line (the stub writer calls a hook) and ran the hourly
sweep every 300 ms.

| Check | Result |
| --- | --- |
| Upload once, streamed to the private directory, named by a random id | pass |
| Preview from the stored file: headers, `rowCount` 60,000 | pass |
| Validate job: `done`, nothing written, the file kept for the import | pass |
| Import job polled to completion: progress never decreases, ends at 1, all 60,000 rows written; the file deleted after | pass |
| Cancel after 3 batches: `cancelled`, `ABORTED`, `details` `{ rowsRead: 1500, imported: 1500, failed: 0 }`; every started batch finished; none started after | pass |
| Cancel: the uploaded file deleted | **fail** (R1-1) |
| A process killed mid-import (SIGKILL) leaves its file; a restarted process's sweep removes it once it is older than the TTL | pass |
| A fresh upload is not swept | pass |

### d. Grouping by default

`suggestMapping` with a sample proposes the group for the order fixture. `runImport` with no
`grouping` option, for CSV and `.xlsx` alike, gives exactly `applyMapping`'s records, errors and
warnings. `grouping: false` refuses with `INVALID_PLAN` and `PLAN_GROUP` (`grouping-disabled`),
and writes nothing. `contiguous: false` is still refused by default (`non-contiguous`).

### e. Binary refusal

Each file went through `readSheet`, `previewSheet`, `runImport`, `readSheetFile` and
`readCsvFile`:

| File | Result |
| --- | --- |
| A real PNG (26 KB), renamed `.csv` | identical: `UNSUPPORTED_FORMAT`, the binary message |
| A real JPEG (542 KB), renamed `.xlsx` | identical |
| A real PDF (W3C's `dummy.pdf`, 13 KB), as `.pdf` and renamed `.csv` | identical |
| A zip of a CSV (`Compress-Archive`), as `.zip` and renamed `.xlsx` | same code, `readCsvFile`'s message differs (R1-2) |

### f. Modules and typings

- **CommonJS and ESM:** both builds resolve. Each ran `runImport` with `signal` and
  `onProgress` (the final call `{ bytesRead: <size>, rowsRead: 2000 }`), got `ABORTED` (499) for a
  signal aborted up front, the binary refusal from `readCsvFile`, `SERVER_FEATURES` from the main
  entry, and read a workbook. Every removed name was absent from `/node`, while `templateOf` and
  `templateFilename` were present.
- **Jest:** a CommonJS project with no Node flags received an upload over `node:http`, and a
  run cancelled from `onBatch` answered 499 `ABORTED` with
  `{ rowsRead: 200, imported: 200, failed: 0 }` after exactly two batches.
- **TypeScript 7.0.2 and 5.9.3:** strict, `skipLibCheck` off, `NodeNext` and `bundler`, and a
  `.cts` file. The 2.0 types (`ImportProgress`, `signal`, `onProgress`, `ABORTED`) compile, and
  `@ts-expect-error` confirms that `UNKNOWN_ENTITY`, `totalTimeoutMs`, `createImportRouter`,
  `sendFailure`, `safeFieldName`, `ImportBinding` and `/node`'s `SERVER_FEATURES` are gone. 0
  errors.

### g. Browsers

Vite 8.3.4, Playwright 1.64.1: 25/25 in each browser, as 1.1 rc.2 was. That held again under
`TZID=Pacific/Kiritimati`. Only the app chunk loads up front and after every CSV; the ExcelJS
chunk loads with the first workbook. With `deflate-raw` taken away, each browser reads a CSV and
refuses a workbook with `UNSUPPORTED_RUNTIME`. The PNG and the PDF are refused in each browser
with the server's code and message.
