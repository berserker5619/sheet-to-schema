# sheet-to-schema 1.1 release-candidate feedback

Findings from testing the published 1.1 release candidates in fresh projects outside the
repository, installed from npm, never from this repository's source. Nothing here is fixed in
the round that found it. The scripts are in [`test-harness/1.1-rc2/`](../test-harness/1.1-rc2/README.md).

Severity: **High** blocks the release; **Medium** is wrong behaviour a user can meet, to fix
before 1.1.0; **Low** is a rough edge or a documentation gap; **Info** is worth knowing and
needs no change.

## Round 1: 1.1.0-rc.2 (2026-10-18)

`sheet-to-schema@next` = `1.1.0-rc.2`, host Node v24.19.0 on Windows 11.

| Case | What | Result |
| --- | --- | --- |
| a | `readSheetFile` and `readXlsx` in real browsers against the server's `readSheet` | **pass**, with one finding (R1-1) |
| b | CSV-only app with Vite, webpack, esbuild: no ExcelJS up front, fetched on the first workbook | pass |
| c | `createImportRouter` with grouping on and off, express 4 and 5, CommonJS and ESM | pass |
| d | (c) in a CommonJS Jest project with no Node flags | pass |
| e | Strict TypeScript, `skipLibCheck` off, `@types/express` 4, 5 and none | pass |

### Findings

| ID | Severity | Finding | Case |
| --- | --- | --- | --- |
| R1-1 | Medium | On a runtime that has `DecompressionStream` but not its `deflate-raw` format, reading a workbook through `/browser` throws a raw `TypeError` (`ERR_INVALID_ARG_VALUE: The argument 'format' is invalid. Received 'deflate-raw'`) instead of the reader's own "cannot read .xlsx files" message. That is Node 20.0 to 20.11 (verified) and, by MDN's data, Chrome and Edge 80 to 102. The README and the `/browser` entry say it runs in "Node 20"; for a workbook it needs Node 20.12. A CSV reads on all of them. | a |
| R1-2 | Low | The README gives no minimum browser versions for reading a workbook in the browser. They are those of `DecompressionStream('deflate-raw')`: Chrome and Edge 103, Firefox 113, Safari 16.4 (iOS 16.4), Node 20.12 (by MDN; Node verified). | a |
| R1-3 | Info | esbuild, with code splitting, also loads a 367-byte shared chunk up front (246 bytes gzipped). It holds no ExcelJS. | b |
| R1-4 | Info | The order fixture has one valid order of four, by design (the other three carry the errors the prototype seeded), so a grouped HTTP import of it writes one record. The other three are compared by their errors and warnings, which match `applyMapping` exactly. | c |

**R1-1 in detail.** rc.2's `inflate` checks `typeof DecompressionStream !== 'function'` and gives
its message only when the class is missing. A runtime that has the class but rejects the format
throws from the constructor, outside the reader's `try`, so the `TypeError` escapes as it is:

```
v20.11.0 case3_excel_semicolon.csv OK Product|Price|Rating
v20.11.0 case1_1904_dates.xlsx FAILED TypeError ERR_INVALID_ARG_VALUE The argument 'format' is invalid. Received 'deflate-raw'
v20.12.0 case3_excel_semicolon.csv OK Product|Price|Rating
v20.12.0 case1_1904_dates.xlsx OK Name|BirthDate|JoinDate
```

`new DecompressionStream('deflate-raw')` across Node releases: 20.0.0, 20.10.0 and 20.11.0 reject
the format; 20.12.0, 20.13.0 and 20.18.0 accept it. CI's Node 20 job passes because it runs a
current 20.x. To fix (not done in this round): detect the format, not just the class, and say
what the runtime lacks; and state the minimums (R1-2) in the README and the entry's comment.

### a. Real browsers

A Vite app (`readSheetFile` and `readXlsx` on a `File` fetched from the page, as a user's file
input gives one) in Playwright 1.64.1, compared value for value with what the published
server `readSheet` reads from the same bytes (dates compared as instants).

| Browser | Checks | `DecompressionStream('deflate-raw')` |
| --- | --- | --- |
| Chromium 156.0.8078.4 | 25/25 | yes |
| Firefox 157.0 | 25/25 | yes |
| WebKit 27.2 | 25/25 | yes |

25 checks: 16 fixtures through `readSheetFile` and the 9 workbooks again through `readXlsx`.

- CSV: Excel "CSV UTF-8" with a byte-order mark; Excel semicolon with decimal commas (reported
  separator `;`); a `.tsv` read as tabs by its name though its header has more commas; the Google
  Sheets export with a multi-line quoted cell and escaped quotes; Tamil and emoji; ragged rows;
  blank lines.
- xlsx: 1904 dates; numeric identifiers including an unsafe integer; the complex sheet (merged
  header, hidden column, formulas, two sheets, trailing styled rows, duplicate headers); the
  openpyxl emoji workbook ("Rajesh Kumar 🎉" intact); Tamil; typed cells; error cells; blank
  rows; formula results, including cached `0`, `false` (plain and shared), errors and dates.
- The same 25/25 in all three browsers with the page in `America/Los_Angeles` and in
  `Pacific/Kiritimati`: dates do not depend on the browser's time zone.
- `readXlsx` failed in no browser.

Minimum versions for reading a workbook, from MDN browser-compat-data 8.1.6 (2026-10-15),
`DecompressionStream` format `deflate-raw`: Chrome 103, Edge 103, Firefox 113, Safari 16.4,
Safari on iOS 16.4, Chrome Android 103, Firefox Android 113; Node 21.2.0 by the data, 20.12.0
by test (the format was backported to 20.x). The class alone is older (Chrome 80, Firefox 113,
Safari 16.4), which is what R1-1 is about. Only current versions were run; the minimums are the
data's, not tested.

### b. Bundles

The same CSV-only app (`import { readSheetFile } from 'sheet-to-schema/browser'`), built three
ways. "Up front" is the entry and every chunk it imports statically. ExcelJS was looked for by a
string only it contains ("Worksheet name already exists").

| Bundler | Up front, bytes | gzipped | ExcelJS up front | ExcelJS chunk, bytes | Fetched |
| --- | --- | --- | --- | --- | --- |
| Vite 8.3.4 | 16,534 | 6,896 | no | 929,394 (255,508 gzipped) | on the first workbook |
| webpack 5.112.0 | 16,020 | 6,609 | no | 940,974 | on the first workbook |
| esbuild 0.28.2 | 13,473 + 367 (R1-3) | 5,656 + 246 | no | 946,156 | on the first workbook |

Each build was also run in Chromium: 25/25, and the scripts requested were the up-front ones
until the first workbook was read, then the ExcelJS chunk.

### c. Server

`createImportRouter` with `grouping: true` and without, express 4.22.3 and 5.3.0, each as a
CommonJS and an ESM script, over HTTP (`fetch` and `FormData`) with the order fixture's suggested
plan (grouped by Order ID). All four combinations pass every check:

- preview lists `features: ["group"]` with grouping on and has no `features` with it off;
  `planForServer(plan, preview)` sends the plan to the first and refuses it (`['group']`) for the
  second;
- `/validate` with grouping on answers `written: false`, stores nothing, and reports exactly
  `applyMapping`'s counts, errors (5) and warning (1);
- `/import` of the order fixture as CSV and as `.xlsx` writes exactly `applyMapping`'s records,
  and `rowsInImported + skipped + failed === rowsRead`;
- NF-1001's second row moved to the end: 422 `GROUP_NOT_CONTIGUOUS`, `details` key `["NF-1001"]`,
  rows `[2, 8]`;
- grouping off: `/validate` and `/import` answer 400 `INVALID_PLAN` carrying `PLAN_GROUP` with
  1.0's message, and nothing is written.

### d. Jest

The same checks as a test in a CommonJS Jest 30.5.2 project, run with `NODE_OPTIONS` unset:
passes. (The test asserts with Jest's `expect`: `node:assert`'s strict deep-equality compares
prototypes, and what `fetch` parses is built in Node's realm, not the test sandbox's. A harness
matter, not the package's.)

### e. Typings

TypeScript 5.9.3, `--strict --skipLibCheck false`, `lib` ES2022 and DOM, with `nodenext` and
with `bundler` resolution: the browser entry (`readSheetFile`, `readXlsx`, `ImportError`,
`BrowserLimits`, `SheetFile`, `SheetFileInput`), `GroupLimits`, `ServerCapabilities`,
`ImportPreviewResponse.features`, `planForServer` in both forms, `runImport` and
`createImportRouter` with `grouping`, and `@ts-expect-error` on a non-boolean `grouping` and on
a server-only limit in `BrowserLimits`. Compiles against `@types/express` 4.17.25 and 5.0.6 (with
an express app mounting a grouping router) and with no `@types/express` at all.

### Harness notes

Two mistakes in the harness itself were found and fixed during the round; neither is the
package's. The server reference first wrote its dates as strings (a serializer that did not
descend into the top-level object), which made every date-holding workbook look different in
every browser. And a typing helper first returned the structural `ImportRouter` instead of the
router it was given, which express's `app.use` rejects; written generically, as
`createImportRouter` is, it compiles.

### Outcome

Not released. R1-1 is a Medium: 1.1.0 waits for its fix and for R1-2's minimum versions in the
README. Both are in 1.1.0-rc.3 (Round 2).

## Round 2: 1.1.0-rc.3 (2026-10-18)

`sheet-to-schema@next` = `1.1.0-rc.3`, the same harness, the same projects upgraded to it, the
server reference regenerated from it. rc.3 is rc.2 with R1-1 and R1-2 fixed: before reading a
workbook, `/browser` checks `new DecompressionStream('deflate-raw')` and refuses an unsupported
runtime with `UNSUPPORTED_RUNTIME`, naming the minimum versions, which the README now lists.

| Case | What | Result |
| --- | --- | --- |
| a | Vite build in Chromium 156, Firefox 157, WebKit 27.2; also in `America/Los_Angeles` and `Pacific/Kiritimati` | pass: 25/25 in every browser and zone |
| a | Each browser with `DecompressionStream` rejecting `"deflate-raw"` (as Chrome and Edge 80-102) | pass: a CSV reads, a workbook gets `UNSUPPORTED_RUNTIME` with the minimums |
| a | Node 20.11.0 and 20.12.0, `old-node.mjs` | pass: 20.11 reads the CSV and refuses the workbook with `UNSUPPORTED_RUNTIME`; 20.12 reads both |
| b | Vite, webpack and esbuild builds, each in all three browsers | pass: 25/25 each; no ExcelJS up front; its chunk fetched on the first workbook |
| c | express 4.22.3 and 5.3.0, CommonJS and ESM, grouping on and off | pass, every check as in Round 1 |
| d | CommonJS Jest 30.5.2, no Node flags | pass |
| e | TypeScript 5.9.3 strict, `skipLibCheck` off, `@types/express` 4.17.25, 5.0.6 and none; `nodenext` and `bundler` | pass |

Bundle sizes up front, in bytes (ExcelJS chunk unchanged from Round 1): Vite 16,721; webpack
16,191; esbuild 13,657 + 367. Each grew by under 200 bytes, the runtime check and its message.

What Node 20.11 now says:


Dynamic Entity's drift workflow passed against rc.3 on `@next` and 1.0.0 on `@latest`, 1238,
352 and 148 tests each ([run 39118400223](https://github.com/berserker5619/Dynamic-Entity/actions/runs/39118400223)).

No findings. **Outcome:** 1.1.0 prepared, its code identical to rc.3.
